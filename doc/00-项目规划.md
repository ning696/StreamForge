# StreamForge 项目计划方案

## 1. 项目概述

### 1.1 项目定位

StreamForge 是一个基于 Web 的实时音视频会议系统。`livekit-standalone-cluster` 分支的 MVP 采用 **LiveKit 独立集群承载 SFU**：StreamForge 负责用户、房间、聊天、Token 签发和产品界面，LiveKit 负责 WebRTC 信令、ICE、媒体轨道发布订阅和 SFU 转发。

### 1.2 核心架构

- **架构模式**：SFU + LiveKit 独立集群 + StreamForge 房间服务
- **后端技术栈**：Go 房间服务 + Java 用户服务 + LiveKit + MySQL + Redis
- **前端技术栈**：Vue 3 + TypeScript + Element Plus + `livekit-client`
- **部署方式**：Docker Compose + Kubernetes Manifest，MVP 阶段支持 LiveKit 独立部署和后续多节点扩展

> **当前范围**：本文档 §2.1 的 MVP 功能为当前实施范围，包含 Vue 前端、Go 房间服务、Java 简单用户服务、MySQL 用户数据存储、LiveKit 独立集群、Redis 运行时协调与 Kubernetes 部署。§2.2 / §2.3 为后续规划，不在当前迭代内。

### 1.3 项目优势

#### 1.3.1 技术优势

- 使用成熟 LiveKit 承担 WebRTC/SFU 底层复杂度，降低 SDP、ICE、Track 转发和浏览器兼容风险
- Go 服务聚焦房间入口、Token 签发、聊天和业务状态，服务边界更清晰
- LiveKit 支持多参与者实时音视频、屏幕共享、媒体控制和后续集群扩容
- 保留 Java + MySQL 的简单用户体系，便于后续扩展完整鉴权和业务数据

#### 1.3.2 用户体验优势

- 无需安装客户端，通过浏览器即可访问
- 支持跨平台使用（桌面、移动设备）
- 使用 LiveKit SDK 获得更成熟的音视频连接、重连、订阅和设备控制体验

#### 1.3.3 开发与测试优势

- 可通过多标签页模拟多用户测试
- 避免 MVP 阶段投入大量自研 SFU 调试成本
- 支持容器化一键部署，LiveKit 可独立替换为本地、私有化或云托管部署

## 3. 技术方案

### 3.1 架构设计

#### 3.1.1 架构选型：SFU vs P2P vs MCU

| 架构类型 | 适用场景 | 优势 | 劣势 |
|:---|:---|:---|:---|
| **P2P** | 2-3 人会议 | 延迟最低，服务器压力小 | 客户端带宽需求随人数指数增长 |
| **SFU** | 4-10 人会议 | 客户端上行带宽需求低，服务器无需混流转码 | 客户端下行带宽需求较高，需要媒体服务器 |
| **MCU** | 10 人以上大型会议 | 客户端带宽需求最小 | 服务器 CPU 消耗高，实现复杂 |

本项目继续选择 SFU 架构，但不再由 StreamForge Go 服务自研 SFU。MVP 使用 LiveKit 独立集群作为媒体底座，原因如下：

- 目标场景为 4-8 人会议，SFU 架构性能和体验更合适
- LiveKit 已封装 WebRTC 信令、ICE、Track 发布订阅、重连、屏幕共享和设备控制
- StreamForge 可以专注业务房间、用户体系、聊天和部署集成
- 后续录制、Egress、TURN、监控和集群能力有成熟扩展路径

#### 3.1.2 系统架构图（MVP）

```text
┌───────────────┐
│ Web Browser   │
│ Vue3 + TS     │
│ livekit-client│
└───────┬───────┘
        │ REST 登录/用户信息
        ▼
┌────────────────────┐       ┌─────────────────┐
│ Java 用户服务       │──────▶│      MySQL       │
│ Spring Boot        │       │ 用户账号数据      │
└────────────────────┘       └─────────────────┘
        │
        │ REST 创建/加入房间，获取 LiveKit Token
        ▼
┌────────────────────┐       ┌────────────────────┐
│ Go 房间服务         │──────▶│ Redis 可过期业务状态 │
│ room + token + chat│       │ room meta / online │
└──────┬─────────────┘       └────────────────────┘
       │ WebSocket 可选：聊天/业务消息
       │
       │ LiveKit SDK：音视频/屏幕共享/媒体状态
       ▼
┌────────────────────────────────────────────────┐
│              LiveKit 独立集群                    │
│                                                │
│  livekit-1       livekit-2       livekit-3      │
│  ┌─────────┐     ┌─────────┐     ┌─────────┐   │
│  │ WebRTC  │     │ WebRTC  │     │ WebRTC  │   │
│  │ SFU     │     │ SFU     │     │ SFU     │   │
│  │ RTC UDP │     │ RTC UDP │     │ RTC UDP │   │
│  └─────────┘     └─────────┘     └─────────┘   │
│          └──────────▶ Redis 集群协调 ◀─────────┘│
└────────────────────────────────────────────────┘
```

MVP 约束：WebRTC 对象、SDP、ICE Candidate、RTP/RTCP、媒体 Track 和 SFU 转发都属于 LiveKit。StreamForge 的 Redis 不再保存 `roomId -> mediaInstanceId` 的媒体路由；可保存业务房间摘要、聊天在线状态等可过期数据。

### 3.2 技术选型

#### 3.2.1 后端技术栈（MVP）

| 技术组件 | 选型 | 选型理由 |
|:---|:---|:---|
| 房间服务语言 | **Go 1.21+** | 适合实现轻量 REST/WebSocket、Token 签发和高并发业务消息 |
| 用户服务语言 | **Java 17+ / Spring Boot** | 适合实现用户注册、登录校验、账号资料等业务逻辑 |
| SFU 媒体服务 | **LiveKit Server** | 成熟的开源 WebRTC SFU，支持 JS SDK、自托管、Docker 和 Kubernetes |
| 前端媒体 SDK | **livekit-client** | 处理房间连接、Track 发布订阅、屏幕共享、媒体控制和重连 |
| WebSocket 库 | **gorilla/websocket** | 用于 StreamForge 自有聊天或业务实时消息 |
| 业务数据库 | **MySQL** | 存储用户账号、密码哈希、用户名，后续可扩展会议历史与聊天记录 |
| 协调缓存 | **Redis** | LiveKit 集群协调；StreamForge 可保存可过期房间摘要和在线状态 |

#### 3.2.2 前端技术栈

| 技术组件 | 选型 | 选型理由 |
|:---|:---|:---|
| 前端框架 | **Vue 3 + TypeScript** | 组合式 API，类型安全，团队约定 |
| 构建工具 | **Vite** | Vue 3 官方推荐，热更新快 |
| 状态管理 | **Pinia** | Vue 3 官方推荐，TS 友好 |
| 音视频 SDK | **livekit-client** | 比直接使用浏览器原生 WebRTC API 更适合快速交付 MVP |
| UI 组件库 | **Element Plus** | 组件生态成熟，适合快速构建会议系统常用界面 |
| 桌面端封装（远期） | **Electron / Tauri** | 复用 Vue 前端代码，产出桌面客户端 |

#### 3.2.3 部署方案

| 组件 | 技术选型 | 说明 |
|:---|:---|:---|
| 容器化 | **Docker** | 前端、Go 房间服务、Java 用户服务、LiveKit、MySQL、Redis 均提供容器化运行方式 |
| 编排工具 | **Kubernetes** | MVP 阶段提供 Manifest，LiveKit 独立部署并规划 RTC 端口 |
| 本地/开发 | **Docker Compose** | 本地一键启动前端、用户服务、房间服务、LiveKit、MySQL、Redis |
| 反向代理 / 入口 | **Nginx Ingress / 网关入口** | 代理 REST、WebSocket、LiveKit 信令；RTC UDP 端口单独规划 |
| 业务数据库 | **MySQL** | 存储用户账号数据 |
| 协调缓存 | **Redis** | LiveKit 集群协调和 StreamForge 运行时摘要 |
| 镜像仓库 | **Harbor / 私有 Registry** | 镜像版本管理 |

### 3.3 架构演进：MVP 边界与远期规划

| 服务 / 组件 | 阶段 | 技术选型 | 职责 |
|:---|:---:|:---|:---|
| **前端应用** | MVP | Vue 3 + TypeScript + Element Plus + livekit-client | 登录/注册页面、房间页面、视频宫格、聊天面板、媒体控制 |
| **房间服务** | MVP | Go + REST + WebSocket + LiveKit Server SDK | 房间创建/加入、LiveKit Token 签发、聊天广播、业务在线状态 |
| **媒体服务** | MVP | LiveKit Server | WebRTC 信令、SFU 转发、屏幕共享、媒体状态、参与者事件 |
| **用户服务** | MVP | Java + Spring Boot | 简单注册、登录校验、用户信息查询；暂不做完整鉴权 |
| **业务数据库** | MVP | MySQL | 存储用户账号数据，后续扩展会议历史、聊天记录等持久化业务数据 |
| **运行时缓存** | MVP | Redis | LiveKit 集群协调；StreamForge 可保存可过期房间摘要和临时在线状态 |
| **录制服务** | P1 | LiveKit Egress / Go | 订阅 LiveKit 房间流并导出录制文件 |
| **API 网关** | P1 | Go / Nginx / Ingress | 统一入口、鉴权透传、限流、路由聚合 |

**MVP 明确不做的能力**：

- 不做 JWT / Session / OAuth2 等完整鉴权，只做账号、密码、用户名的注册与登录校验。
- 不做房间历史、聊天记录、会议记录的持久化查询。
- 不在 StreamForge Go 服务中自研 WebRTC SFU。
- 不在 MySQL 或 Redis 中保存 WebRTC 对象、PeerConnection、SDP、ICE Candidate 或 Track。
- 不做完整 Helm Chart、灰度发布、自动扩缩容策略和全量可观测体系，仅提供可运行的 K8s Manifest。

**语言分工的考量**：

- **Go**：房间入口、LiveKit Token 签发、WebSocket 业务消息、后续录制或集成服务。
- **Java**：用户业务、数据持久化、后续鉴权和后台管理能力。
- **LiveKit**：音视频媒体链路和 SFU 能力。

## 4. 开发计划

### 4.1 开发路线图

本项目 MVP 采用渐进式开发策略，分三个阶段完成。阶段二直接接入 LiveKit 独立集群，不再投入自研 Pion SFU。

#### 阶段一：用户服务、房间服务与前端骨架（Week 1-2）

**目标**：搭建 Java 用户服务、Go 房间服务骨架、Vue 3 前端骨架和房间内聊天能力。

- 搭建 Java Spring Boot 用户服务，提供注册、登录校验、用户信息查询接口
- 设计 MySQL 用户表，包含用户 ID、账号、密码哈希、用户名、创建时间、更新时间等字段
- 搭建 Go 房间服务基础架构（`gateway` / `room` / `livekit` / `signaling` / `chat` / `state` / `config` 分包）
- 开发房间创建 / 加入 / 离开 REST 接口，先返回房间基础信息
- 基于 gorilla/websocket 实现房间内实时文字聊天
- 搭建 Vue 3 + TS + Vite 前端工程，接入 Pinia、路由、Element Plus、登录/注册页与聊天面板 UI

**交付物**：

- 可运行的 Java 用户服务 + MySQL 用户表
- 可运行的 Go 房间服务 + WebSocket 聊天
- Vue 3 前端可注册 / 登录、创建 / 加入房间，房间内文字聊天可用

#### 阶段二：LiveKit SFU 音视频通话（Week 3-5）

**目标**：接入 LiveKit 独立集群，完成 4-8 人多人音视频房间。

- 在本地 Docker Compose 中加入 LiveKit 和 Redis 配置
- Go 房间服务接入 LiveKit Server SDK 或 JWT 签发逻辑
- 创建/加入房间时生成 `livekitRoomName`、`livekitParticipantIdentity` 和 `livekitToken`
- 前端安装并封装 `livekit-client`
- 房间页使用 LiveKit SDK 连接房间、发布摄像头和麦克风、订阅远端 Track
- 完成 2 人和 4 人浏览器标签页音视频验收
- 保留 Go WebSocket 聊天，或在该阶段评估迁移到 LiveKit data packet

**交付物**：

- 基于 LiveKit 的多人音视频房间
- 聊天面板、用户身份信息与视频界面完成集成
- 本地 Compose 可启动完整音视频链路

#### 阶段三：媒体控制、屏幕共享与 Kubernetes 交付（Week 6-7）

**目标**：补齐 MVP 必备能力，完成容器化与 K8s 部署。

- 屏幕共享（LiveKit SDK `setScreenShareEnabled`）
- 媒体控制（静音、关闭视频、切换设备）
- 在线状态与参与人数实时同步
- 编写前端、Go 房间服务、Java 用户服务的 Dockerfile
- 编写 docker-compose，包含前端、房间服务、用户服务、LiveKit、MySQL、Redis
- 编写 K8s Manifest（Deployment / Service / Ingress / ConfigMap / Secret），明确 LiveKit 信令、RTC UDP、TURN、Redis 配置
- 明确 HTTPS、本地开发与生产部署的差异

**交付物**：

- 完整的视频会议系统 MVP（简单用户体系 + LiveKit 音视频 + 屏幕共享 + 聊天 + 媒体控制 + Docker/K8s 部署）
- Docker 镜像、docker-compose 与 K8s 部署清单

### 4.2 里程碑

| 里程碑 | 目标日期 | 关键成果 |
|:---|:---:|:---|
| M1: 用户、房间与聊天骨架上线 | Week 2 | Java 用户服务 + MySQL + Go 房间服务 + Vue 3 前端 + 房间内实时聊天 |

## 6. 附录

### 6.1 技术术语表

- **SFU（Selective Forwarding Unit）**：选择性转发单元，服务器接收客户端的媒体流并转发给其他客户端，不进行混流转码。
- **LiveKit**：开源实时音视频平台，本项目 MVP 使用其 Server 和前端 SDK 承载 WebRTC/SFU 能力。
- **LiveKit Token**：由 StreamForge 后端签发的 LiveKit access token，用于允许某个参与者加入指定 LiveKit 房间。
- **业务房间（StreamForge Room）**：StreamForge 展示给用户的房间号和业务上下文，可映射到一个 LiveKit room name。
- **WebRTC**：网页实时通信技术标准。
- **ICE**：交互式连接建立，用于 NAT 穿越。
- **MySQL**：MVP 阶段的业务数据库，用于存储用户账号数据。
- **Redis**：用于 LiveKit 集群协调，以及 StreamForge 可过期运行时状态。
