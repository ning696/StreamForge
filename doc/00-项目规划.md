# StreamForge 项目计划方案

## 1. 项目概述

### 1.1 项目定位
StreamForge 是一个基于 Web 的实时音视频通信系统，采用 SFU（Selective Forwarding Unit，选择性转发单元）架构，媒体服务端使用 Go 语言实现，用户服务使用 Java 实现。本项目旨在构建一个支持多人视频会议、屏幕共享与简单用户体系的跨平台解决方案。

### 1.2 核心架构
- **架构模式**：SFU（选择性转发单元）+ 房间级媒体实例路由
- **后端技术栈**：Go 媒体服务 + Java 用户服务 + WebSocket + WebRTC + MySQL + Redis
- **前端技术栈**：Vue 3 + TypeScript + Element Plus（Web），远期扩展桌面端
- **部署方式**：Docker + Kubernetes 容器化部署，MVP 阶段即支持媒体服务多实例部署

> **当前范围**：本文档 §2.1 的 MVP 功能为当前实施范围，包含多实例 Go 媒体服务、Java 简单用户服务、MySQL 用户数据存储、Redis 房间路由协调与 Kubernetes 部署。§2.2 / §2.3 为后续规划，不在当前迭代内。

### 1.3 项目优势

#### 1.3.1 技术优势
- 完整展示 Go 语言在高并发场景下的处理能力
- 涵盖 WebSocket 信令管理、WebRTC 协商、SFU 转发等核心技术
- SFU 架构在 4-8 人会议场景下性能最优
- MVP 阶段即引入房间级路由与媒体服务多实例部署能力，为后续扩容预留基础

#### 1.3.2 用户体验优势
- 无需安装客户端，通过浏览器即可访问
- 支持跨平台使用（桌面、移动设备）
- 实时音视频传输，低延迟体验

#### 1.3.3 开发与测试优势
- 可通过多标签页模拟多用户测试
- 架构清晰，便于功能扩展
- 支持容器化一键部署

## 3. 技术方案

### 3.1 架构设计

#### 3.1.1 架构选型：SFU vs P2P vs MCU

| 架构类型 | 适用场景 | 优势 | 劣势 |
|:---|:---|:---|:---|
| **P2P** | 2-3 人会议 | 延迟最低，服务器压力小 | 客户端带宽需求随人数指数增长 |
| **SFU** | 4-10 人会议 | 客户端上行带宽需求低，服务器无需编解码 | 客户端下行带宽需求较高 |
| **MCU** | 10 人以上大型会议 | 客户端带宽需求最小 | 服务器 CPU 消耗极高 |

**本项目选择 SFU 架构，原因如下**：
- 目标场景为 4-8 人会议，SFU 架构性能最优
- 服务器仅做流转发，CPU 开销可控
- Go 语言的 goroutine 特性适合处理高并发连接
- 符合主流商业产品（Zoom、Google Meet）的技术选型

#### 3.1.2 系统架构图（MVP）

MVP 阶段采用多服务形态：前端为 Vue 3 + TypeScript + Element Plus 单页应用；Go 媒体服务承担房间、信令、SFU 转发、屏幕共享与聊天广播；Java 用户服务承担简单注册、登录校验与用户信息查询。媒体服务在 Kubernetes 中按多实例部署，通过 Redis 维护 `roomId -> mediaInstanceId` 的房间级路由，保证同一个房间内的参与者连接到同一个媒体实例。

```
┌─────────────┐      ┌────────────────────┐
│  Web 客户端  │─────▶│  前端 SPA           │
│ Vue3 + TS   │      │  Element Plus       │
└──────┬──────┘      └────────────────────┘
       │ REST 登录/用户信息
       ▼
┌────────────────────┐       ┌─────────────────┐
│ Java 用户服务       │──────▶│      MySQL       │
│ Spring Boot        │       │ 用户账号数据      │
└────────────────────┘       └─────────────────┘
       │
       │ 创建/加入房间，获取媒体实例路由
       ▼
┌────────────────────┐       ┌─────────────────┐
│ Go 媒体路由/信令入口 │──────▶│      Redis       │
│ room routing       │       │ room -> instance │
└──────┬─────────────┘       │ 实例心跳/临时状态 │
       │                     └─────────────────┘
       │ WebSocket + WebRTC
       ▼
┌────────────────────────────────────────────────┐
│              Go 媒体服务多实例                  │
│                                                │
│  media-service-1   media-service-2   media-service-3
│  ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│  │ Room A/B    │   │ Room C      │   │ Room D/E    │
│  │ signaling   │   │ signaling   │   │ signaling   │
│  │ sfu tracks  │   │ sfu tracks  │   │ sfu tracks  │
│  │ chat        │   │ chat        │   │ chat        │
│  └─────────────┘   └─────────────┘   └─────────────┘
└────────────────────────────────────────────────┘
```

MVP 多实例约束：同一个房间固定到一个媒体实例；Redis 仅保存房间路由、媒体实例心跳和必要的临时状态摘要；真实的 WebSocket 连接、RTCPeerConnection、媒体 Track 等对象仍保存在对应 Go 媒体实例的进程内存中。MVP 不实现同一房间跨多个媒体实例的媒体级联转发。

### 3.2 技术选型

#### 3.2.1 后端技术栈（MVP）

| 技术组件 | 选型 | 选型理由 |
|:---|:---|:---|
| 媒体服务语言 | **Go 1.21+** | 高并发支持，原生协程，适合低延迟网络 I/O 与 SFU 媒体转发 |
| 用户服务语言 | **Java 17+ / Spring Boot** | 适合实现用户注册、登录校验、账号资料等业务逻辑 |
| WebRTC 库 | **pion/webrtc** | Go 生态最成熟的 WebRTC 实现 |
| WebSocket 库 | **gorilla/websocket** | 业界标准，社区活跃 |
| 业务数据库 | **MySQL** | 存储用户账号、密码哈希、用户名，后续可扩展会议历史与聊天记录 |
| 协调缓存 | **Redis** | 存储媒体实例注册、实例心跳、`roomId -> mediaInstanceId` 房间级路由与临时在线状态 |

#### 3.2.2 前端技术栈

| 技术组件 | 选型 | 选型理由 |
|:---|:---|:---|
| 前端框架 | **Vue 3 + TypeScript** | 组合式 API，类型安全，团队约定 |
| 构建工具 | **Vite** | Vue 3 官方推荐，热更新快 |
| 状态管理 | **Pinia** | Vue 3 官方推荐，TS 友好 |
| WebRTC API | **浏览器原生 API** | 无需额外依赖，兼容性好 |
| UI 组件库 | **Element Plus** | 组件生态成熟，适合快速构建表单、弹窗、布局、通知等会议系统常用界面 |
| 桌面端封装（远期） | **Electron / Tauri** | 复用 Vue 前端代码，产出桌面客户端 |

#### 3.2.3 部署方案

| 组件 | 技术选型 | 说明 |
|:---|:---|:---|
| 容器化 | **Docker** | 前端、Go 媒体服务、Java 用户服务、MySQL、Redis 均提供容器化运行方式 |
| 编排工具 | **Kubernetes** | MVP 阶段即提供 Manifest，媒体服务按多副本部署并保留实例身份 |
| 本地/开发 | **Docker Compose** | 本地一键启动前端、用户服务、媒体服务、MySQL、Redis，简化联调 |
| 反向代理 / 入口 | **Nginx Ingress / 网关入口** | 代理 REST 与 WebSocket，处理 HTTPS 终止；WebRTC 媒体端口需在部署文档中单独规划 |
| 业务数据库 | **MySQL** | 存储用户账号数据，MVP 可使用单实例数据库或外部托管数据库 |
| 协调缓存 | **Redis** | 存储媒体实例心跳、房间路由与临时在线状态，支撑媒体服务多实例 |
| 镜像仓库 | **Harbor / 私有 Registry** | 镜像版本管理 |

### 3.3 架构演进：MVP 边界与远期规划

MVP 不再采用单一 Go 进程承载全部能力，而是从第一阶段开始采用前端、Go 媒体服务、Java 用户服务、MySQL、Redis 的基础多服务形态。远期演进重点不再是“是否拆服务”，而是在已有边界上补齐鉴权、历史数据、录制、观测与更复杂的媒体扩容能力。

| 服务 / 组件 | 阶段 | 技术选型 | 职责 |
|:---|:---:|:---|:---|
| **前端应用** | MVP | Vue 3 + TypeScript + Element Plus | 登录/注册页面、房间页面、视频宫格、聊天面板、媒体控制 |
| **媒体服务（Media / SFU）** | MVP | Go + pion/webrtc + gorilla/websocket | 房间管理、WebRTC 信令、SFU 媒体流转发、屏幕共享、聊天广播 |
| **媒体路由协调** | MVP | Redis + Go 路由模块 | 媒体实例注册、实例心跳、`roomId -> mediaInstanceId` 路由分配 |
| **用户服务（User）** | MVP | Java + Spring Boot | 简单注册、登录校验、用户信息查询；字段为账号、密码、用户名；暂不做鉴权 |
| **业务数据库** | MVP | MySQL | 存储用户账号数据，后续扩展会议历史、聊天记录等持久化业务数据 |
| **API 网关** | P1 | Go | 统一入口、鉴权透传、限流、路由聚合、WebSocket 长连接治理 |
| **应用服务（App）** | P1 | Java | 房间历史记录、会议纪要、聊天记录查询、统计等应用层业务 |
| **录制服务（Recorder）** | P1 | Go | 订阅 SFU 流并落盘为 MP4，独立部署避免影响实时链路 |

**MVP 明确不做的能力**：
- 不做 JWT / Session / OAuth2 等完整鉴权，只做账号、密码、用户名的注册与登录校验。
- 不做房间历史、聊天记录、会议记录的持久化查询。
- 不做同一房间跨多个媒体实例的媒体级联转发；同一个房间固定在一个媒体实例内完成 SFU 转发。
- 不做完整 Helm Chart、灰度发布、自动容量调度和全量可观测体系，仅提供可运行的 K8s Manifest。

**语言分工的考量**：
- **Go**：贴近网络 I/O、并发密集、对延迟敏感的链路（媒体、信令、路由、录制）。
- **Java**：贴近业务逻辑、数据持久化、后续鉴权和后台管理能力（用户、查询、应用层业务）。

**服务间协作**：
- MVP 同步调用以 **REST** 为主，前端分别调用用户服务与媒体服务入口。
- MVP 运行时协调以 **Redis** 为主，用于房间路由、媒体实例心跳与临时在线状态。
- 远期内部服务可引入 **gRPC**，异步事件可引入 **Kafka / NATS**。
- 远期可观测性可引入 **Prometheus + Grafana + Loki + OpenTelemetry**。

## 4. 开发计划

### 4.1 开发路线图

本项目 MVP 采用渐进式开发策略，分三个阶段完成。**跳过 P2P 中间态，阶段二直接进入多实例 SFU 架构**——避免为一次性的 P2P 实现投入返工成本，也让服务端从第一天起围绕房间级路由与媒体转发链路设计。

#### 阶段一：用户服务、信令服务与路由骨架（Week 1-2）
**目标**：搭建 Java 用户服务、Go 媒体服务骨架、Redis 房间路由基础与 Vue 3 前端骨架

- 搭建 Java Spring Boot 用户服务，提供注册、登录校验、用户信息查询接口
- 设计 MySQL 用户表，包含用户 ID、账号、密码哈希、用户名、创建时间、更新时间等字段
- 搭建 Go 媒体服务基础架构（`gateway` / `router` / `instance` / `signaling` / `room` / `chat` / `sfu` 分包）
- 基于 Redis 实现媒体实例注册、实例心跳、房间路由分配骨架
- 基于 gorilla/websocket 实现 WebSocket 连接管理
- 开发房间创建 / 加入 / 离开逻辑，加入房间时必须经过 `roomId -> mediaInstanceId` 路由判断
- 实现 **实时文字聊天**（同一房间内广播，同时验证信令通道）
- 搭建 Vue 3 + TS + Vite 前端工程，接入 Pinia、路由、Element Plus、登录/注册页与聊天面板 UI

**交付物**：
- 可运行的 Java 用户服务 + MySQL 用户表
- 可运行的 Go WebSocket 服务 + Redis 房间路由骨架
- Vue 3 前端可注册 / 登录、创建 / 加入房间，房间内文字聊天可用

#### 阶段二：多实例 SFU 音视频通话（Week 3-5）
**目标**：直接以多实例 SFU 架构落地多人音视频（不做 P2P 中间态）

- 集成 pion/webrtc，Go 媒体实例作为 SFU 端点
- 实现 SDP Offer/Answer 协商与 ICE Candidate 交换
- 实现媒体实例启动注册、周期心跳、异常实例路由清理
- 创建房间时按负载或简单轮询选择媒体实例，并写入 Redis 房间路由
- 加入房间时根据 Redis 路由将同一房间用户固定到同一个媒体实例
- 服务端接收每位参与者的上行流，按订阅关系向同房间其他参与者选择性转发下行流
- 前端 WebRTC 客户端（getUserMedia、RTCPeerConnection、多路远端流渲染）
- 支持 4-8 人同房间音视频通话；MVP 不做同房间跨媒体实例级联

**交付物**：
- 基于多实例房间路由的 SFU 多人音视频房间
- 聊天面板、用户身份信息与视频界面完成集成

#### 阶段三：媒体控制与 Kubernetes 交付（Week 6-7）
**目标**：补齐 MVP 必备能力，完成容器化与 K8s 部署

- 屏幕共享（getDisplayMedia + 独立轨道转发）
- 媒体控制（静音、关闭视频、切换设备）
- 在线状态与参与人数实时同步
- 编写前端、Go 媒体服务、Java 用户服务的 Dockerfile
- 编写 docker-compose（本地），包含前端、媒体服务、用户服务、MySQL、Redis
- 编写 K8s Manifest（Deployment / Service / Ingress / ConfigMap / Secret），验证多媒体服务副本下的房间级路由
- 明确 WebRTC 媒体端口、HTTPS、本地开发与生产部署的差异

**交付物**：
- 完整的 SFU 视频会议系统 MVP（简单用户体系 + 视频 + 屏幕共享 + 聊天 + 媒体控制 + 多实例房间路由）
- Docker 镜像、docker-compose 与 K8s 部署清单

|:---|:---:|:---|

## 5. 预期成果

### 5.1 系统能力（MVP 交付）

MVP 阶段交付的系统将具备以下能力：

- 用户通过浏览器访问 Vue 3 + TypeScript + Element Plus 前端，无需安装客户端
- 支持账号、密码、用户名构成的简单用户体系，提供注册、登录校验与用户信息查询
- 使用 MySQL 存储用户账号数据
- 支持动态创建和加入视频会议房间
- 支持 Go 媒体服务多实例部署，并通过 Redis 房间级路由保证同一房间固定到同一媒体实例
- 支持 4-8 人同时进行 SFU 音视频通话
- 提供屏幕共享功能
- 支持基本的媒体控制（静音、关闭视频、切换设备）
- 视频界面内集成实时文字聊天面板，支持房间内广播
- 可通过 Docker Compose 本地运行，并可通过 Kubernetes 部署 MVP 环境

### 5.2 技术价值

本项目将展示以下技术能力：

- Go 语言在高并发、低延迟媒体链路中的应用实践
- Java Spring Boot 在用户业务服务中的应用实践
- MySQL 用户数据建模与持久化实践
- Redis 在媒体实例注册、心跳与房间级路由中的协调实践
- WebSocket 实时信令与聊天通信技术的掌握
- WebRTC 音视频通信协议的深入理解
- 多实例 SFU 架构的设计与实现能力

## 6. 附录

### 6.1 技术术语表

- **SFU（Selective Forwarding Unit）**：选择性转发单元，服务器接收客户端的媒体流并转发给其他客户端，不进行编解码处理
- **媒体实例（Media Instance）**：一个正在运行的 Go 媒体服务副本，内部维护所负责房间的 WebSocket 连接、RTCPeerConnection 和媒体 Track
- **房间级路由**：根据 `roomId` 将同一个房间固定分配到同一个媒体实例的路由策略，MVP 使用 Redis 保存 `roomId -> mediaInstanceId`
- **WebRTC（Web Real-Time Communication）**：网页实时通信技术标准
- **WebSocket**：基于 TCP 的全双工通信协议，用于实时数据传输
- **ICE（Interactive Connectivity Establishment）**：交互式连接建立，用于 NAT 穿越
- **SDP（Session Description Protocol）**：会话描述协议，用于协商媒体参数
- **MySQL**：MVP 阶段的业务数据库，用于存储用户账号数据
- **Redis**：MVP 阶段的运行时协调组件，用于媒体实例心跳、房间路由和临时在线状态
