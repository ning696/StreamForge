# StreamForge MVP 需求规格

## 1. 目标

MVP 阶段交付一个可运行的视频会议系统，支持简单用户体系、多人音视频通话、屏幕共享、文字聊天、媒体控制、在线状态、多实例媒体服务房间级路由，以及 Docker Compose 和 Kubernetes 部署。

MVP 的成功标准是：用户可以注册、登录、创建房间、邀请其他用户加入房间，并在同一房间内完成 4-8 人音视频通话、文字聊天、静音、关闭摄像头和屏幕共享。媒体服务可以运行多个副本，同一房间内所有参与者必须连接到同一个媒体实例。

## 2. 用户角色

| 角色 | 说明 |
|:---|:---|
| 普通用户 | 可以注册账号、登录、创建房间、加入房间、进行音视频会议 |
| 房间创建者 | 创建房间的普通用户；MVP 不提供主持人权限和房间管理特权 |
| 参与者 | 已加入房间的用户；可以发送消息、控制自己的麦克风、摄像头和屏幕共享 |

| 编号 | 功能 | 优先级 | 完成定义 |

## 4. 用户体系需求

### 4.1 注册

用户注册时输入：

- 账号 `account`
- 密码 `password`
- 用户名 `username`

约束：

- `account` 必填、唯一，长度 4-32。
- `password` 必填，长度 6-64。
- `username` 必填，长度 1-32。
- 密码必须在服务端做哈希后存储，数据库不保存明文密码。
- 账号重复时返回明确错误。

### 4.2 登录校验

用户登录时输入：

- 账号 `account`
- 密码 `password`

登录成功返回：

```json
{
  "userId": 1,
  "account": "demo",
  "username": "演示用户"
}
```

MVP 暂不做 JWT、Session、OAuth2、权限校验。前端可以把登录结果保存在本地状态中，并在加入房间时将 `userId` 和 `username` 传给媒体服务。媒体服务在 MVP 阶段信任前端传入的用户基本信息。

### 4.3 用户信息查询

用户服务提供按 `userId` 查询用户基本信息的接口，返回 `userId`、`account`、`username`。接口不返回密码哈希。

## 5. 房间需求

### 5.1 创建房间

用户创建房间时，媒体服务生成唯一 `roomId`。系统根据当前媒体实例状态选择一个可用媒体实例，并把路由写入 Redis：

```text
roomId -> mediaInstanceId
```

创建成功后返回：

- `roomId`
- `mediaInstanceId`
- WebSocket 连接地址
- WebRTC ICE 配置

### 5.2 加入房间

用户加入房间时，系统必须先查询 Redis 中的房间路由。

- 如果房间存在且媒体实例健康，用户连接到该媒体实例。
- 如果房间不存在，返回房间不存在错误。
- 如果房间路由存在但媒体实例不健康，MVP 返回房间不可用错误，不做自动迁移。

### 5.3 离开房间

用户离开房间时：

- 关闭 WebSocket 连接。
- 关闭 WebRTC PeerConnection。
- 从房间成员列表移除该 Peer。
- 广播 `peer_left` 给同房间其他参与者。
- 如果房间为空，释放房间内存状态，并删除或过期 Redis 房间路由。

## 6. 音视频需求

### 6.1 SFU 通话

- 每个参与者向媒体服务上传自己的音频和视频轨道。
- 媒体服务不做编解码混流，只把媒体轨道转发给同房间其他参与者。
- 同一房间所有参与者必须位于同一个媒体实例。
- MVP 支持 4-8 人同房间音视频通话。

### 6.2 屏幕共享

- 屏幕共享使用浏览器 `getDisplayMedia`。
- 屏幕共享作为独立视频轨道发布。
- 同一时间允许多个参与者发起屏幕共享，但前端 MVP 可以优先展示最近开始共享的屏幕。
- 参与者停止共享后，服务端广播屏幕共享停止事件。

### 6.3 媒体控制

媒体控制只影响当前用户自己的媒体轨道状态：

- 静音 / 取消静音
- 关闭摄像头 / 开启摄像头
- 切换麦克风
- 切换摄像头

状态变化需要广播给房间内其他参与者，用于更新 UI。

## 7. 聊天需求

- 聊天消息只在当前房间内广播。
- MVP 不持久化聊天记录。
- 每条聊天消息包含消息 ID、房间 ID、发送者 Peer ID、发送者用户 ID、发送者用户名、消息内容和发送时间。
- 消息内容不能为空，最大长度 1000 字符。

## 8. 多实例需求

### 8.1 媒体实例注册

每个 Go 媒体服务实例启动后需要生成或读取稳定的 `mediaInstanceId`，并向 Redis 写入实例信息和心跳。

实例信息包含：

- `mediaInstanceId`
- `host`
- `httpPort`
- `wsPort`
- `rtcPortRange`
- `startedAt`
- `lastHeartbeatAt`
- `status`

### 8.2 房间级路由

MVP 使用房间级路由：

```text
roomId -> mediaInstanceId
```

规则：

- 创建房间时分配媒体实例。
- 加入房间时必须复用已有房间路由。
- 同一房间不能拆到多个媒体实例。
- Redis 只保存路由和临时状态，不保存 WebRTC 对象。

### 8.3 实例异常

如果媒体实例心跳超时：

- 新房间不再分配到该实例。
- 已在该实例上的房间在 MVP 阶段视为不可用。
- MVP 不做房间迁移，不做媒体连接恢复。

## 9. 部署需求

MVP 需要提供：

- 前端 Dockerfile
- Go 媒体服务 Dockerfile
- Java 用户服务 Dockerfile
- docker-compose 配置
- Kubernetes Deployment / Service / Ingress / ConfigMap / Secret 示例
- MySQL 初始化脚本
- Redis 配置说明

## 10. 非功能需求

| 类别 | 要求 |
|:---|:---|
| 浏览器兼容 | 优先支持最新版 Chrome、Edge；Firefox 作为兼容目标 |
| 通话规模 | MVP 支持单房间 4-8 人 |
| 延迟 | 局域网或良好公网环境下应保持可用的实时互动体验 |
| 可维护性 | 服务边界、协议、数据模型必须有文档对应 |
| 可部署性 | 本地 Docker Compose 和 K8s Manifest 均可启动 MVP 环境 |
| 安全性 | 密码不明文存储；MVP 暂不做完整鉴权 |

## 11. MVP 不包含

- 完整鉴权体系。
- 用户权限、主持人权限、踢人、禁言。
- 房间历史、聊天记录、会议记录持久化查询。
- 录制与回放。
- 同一房间跨媒体实例的媒体级联。
- 自动故障迁移和通话恢复。
- Helm Chart、灰度发布、自动扩缩容策略。
- 虚拟背景、移动原生客户端、桌面客户端。

## 12. 验收标准

MVP 完成时必须满足：

- 用户可以注册并登录。
- 用户可以创建房间并获得房间号。
- 至少两个浏览器标签页可以使用不同用户加入同一房间。
- 同一房间用户可以互相看到视频、听到音频。
- 同一房间用户可以发送和接收聊天消息。
- 用户可以静音、关闭摄像头、恢复媒体轨道。
- 用户可以共享屏幕并停止共享。
- Go 媒体服务运行多个副本时，同一房间仍固定到同一个媒体实例。
- Docker Compose 可以启动完整本地环境。
- Kubernetes Manifest 可以部署前端、媒体服务、用户服务、MySQL 和 Redis。
