# StreamForge 系统架构设计

## 1. 架构目标

MVP 架构需要同时满足三个目标：

1. 快速交付可用的视频会议 MVP。
2. 从第一阶段开始支持媒体服务多实例部署。
3. 保持服务边界清晰，避免后续 Codex 开发时把用户、信令、媒体、路由、前端状态写混。

## 2. 总体架构

```text
Web Browser
  ├─ REST ───────────────▶ Java User Service ─────▶ MySQL
  ├─ REST room routing ──▶ Go Media Service ──────▶ Redis
  └─ WebSocket/WebRTC ───▶ Go Media Instance
```

MVP 由以下组件组成：

| 组件 | 技术 | 职责 |
|:---|:---|:---|
| 前端应用 | Vue 3 + TypeScript + Element Plus | 登录注册、房间页面、视频宫格、聊天、媒体控制 |
| 用户服务 | Java Spring Boot | 注册、登录校验、用户信息查询 |
| 业务数据库 | MySQL | 存储用户账号数据 |
| 媒体服务 | Go + WebSocket + pion/webrtc | 房间、信令、SFU、聊天、屏幕共享 |
| 协调缓存 | Redis | 媒体实例心跳、房间路由、临时在线状态 |
| 部署编排 | Docker Compose + Kubernetes | 本地与 MVP 部署 |

## 3. 核心设计原则

### 3.1 房间级路由

MVP 支持多个 Go 媒体实例，但同一个房间内的所有参与者必须连接到同一个媒体实例。

Redis 保存：

```text
roomId -> mediaInstanceId
```

媒体实例进程内保存：

- WebSocket 连接
- RTCPeerConnection
- 媒体 Track
- 房间成员
- 同房间聊天广播订阅关系

Redis 和 MySQL 不保存 WebRTC 对象。

### 3.2 服务边界

用户服务只关心用户账号数据，不关心房间和媒体。

媒体服务只关心实时通信，不直接写用户数据库。

前端负责组合用户服务和媒体服务的能力。MVP 没有统一 API 网关，前端可以分别调用用户服务和媒体服务入口。

### 3.3 MVP 简化点

- 不做完整鉴权，登录后前端保存用户基本信息。
- 媒体服务信任前端加入房间时传入的 `userId` 和 `username`。
- 不做房间迁移。
- 不做跨媒体实例的媒体级联。
- 不持久化聊天记录。

## 4. 服务职责

### 4.1 前端应用

职责：

- 注册页面。
- 登录页面。
- 创建房间。
- 加入房间。
- 房间视频宫格。
- 聊天面板。
- 参与者列表。
- 媒体控制栏。
- 屏幕共享控制。
- WebSocket 信令连接管理。
- 浏览器 WebRTC 连接管理。

前端不直接访问 MySQL 或 Redis。

### 4.2 Java 用户服务

职责：

- 用户注册。
- 登录校验。
- 用户信息查询。
- 密码哈希。
- 用户账号唯一性校验。

用户服务访问 MySQL，不访问 Redis，不处理 WebRTC。

### 4.3 Go 媒体服务

职责：

- 媒体实例注册与心跳。
- 房间创建、加入、离开。
- 房间级路由分配与查询。
- WebSocket 信令。
- WebRTC Offer / Answer / ICE Candidate 交换。
- SFU 媒体轨道转发。
- 屏幕共享轨道转发。
- 房间内聊天广播。
- 在线成员状态广播。

媒体服务访问 Redis，不直接访问 MySQL。

## 5. Go 媒体服务内部模块

建议分包：

| 包 | 职责 |
|:---|:---|
| `gateway` | HTTP 和 WebSocket 入口、请求上下文、响应封装 |
| `router` | 房间路由分配、路由查询、路由清理 |
| `instance` | 媒体实例 ID、注册、心跳、健康状态 |
| `signaling` | 信令消息类型、解析、校验、分发 |
| `room` | Room、Peer、成员加入离开、在线状态 |
| `chat` | 聊天消息校验和房间内广播 |
| `sfu` | WebRTC PeerConnection、Track 发布订阅、媒体转发 |
| `config` | 环境变量、端口、ICE、Redis 配置 |
| `log` | 结构化日志封装 |

依赖方向：

```text
gateway -> router
gateway -> signaling
signaling -> room
signaling -> chat
signaling -> sfu
router -> instance
router -> Redis
instance -> Redis
room -> sfu
chat -> room
sfu -> room
```

`room` 与 `sfu` 需要避免强循环依赖。实现时可以通过接口隔离，例如 `room` 只暴露 Peer 生命周期，`sfu` 只暴露媒体绑定能力。

## 6. Java 用户服务内部模块

建议包结构：

| 包 | 职责 |
|:---|:---|
| `controller` | REST API 控制器 |
| `service` | 注册、登录校验、用户查询 |
| `repository` | 用户数据访问 |
| `entity` | MySQL 用户实体 |
| `dto` | 请求和响应对象 |
| `config` | 数据源、密码哈希、跨域配置 |
| `exception` | 业务异常和统一错误响应 |

## 7. 关键流程

### 7.1 注册

```text
前端提交 account/password/username
  -> Java 用户服务校验参数
  -> 检查 account 是否存在
  -> 哈希 password
  -> 写入 MySQL
  -> 返回 userId/account/username
```

### 7.2 登录

```text
前端提交 account/password
  -> Java 用户服务查询用户
  -> 校验密码哈希
  -> 返回 userId/account/username
  -> 前端保存用户基本信息
```

### 7.3 创建房间

```text
前端携带 userId/username 请求创建房间
  -> Go 媒体服务查询健康媒体实例
  -> 选择一个 mediaInstanceId
  -> 生成 roomId
  -> 写入 Redis: roomId -> mediaInstanceId
  -> 在目标媒体实例内创建房间内存对象
  -> 返回 roomId、mediaInstanceId、WebSocket 地址、ICE 配置
```

### 7.4 加入房间

```text
前端携带 roomId/userId/username 请求加入
  -> Go 媒体服务查询 Redis roomId -> mediaInstanceId
  -> 如果路由不存在，返回房间不存在
  -> 如果实例不健康，返回房间不可用
  -> 返回目标 WebSocket 地址和 ICE 配置
  -> 前端连接 WebSocket
  -> 前端发起 WebRTC 协商
```

### 7.5 WebRTC 协商

```text
浏览器获取本地媒体
  -> 创建 RTCPeerConnection
  -> 添加本地音视频 Track
  -> 通过 WebSocket 发送 Offer
  -> Go 媒体实例创建/更新 PeerConnection
  -> Go 媒体实例返回 Answer
  -> 双方交换 ICE Candidate
  -> 媒体服务转发同房间参与者 Track
```

## 8. Redis 协调设计

Redis 只负责运行时协调：

- 媒体实例注册。
- 媒体实例心跳。
- 房间到媒体实例的路由。
- 房间临时状态摘要。
- 在线人数缓存。

Redis 不负责：

- 保存用户密码。
- 保存永久会议记录。
- 保存 WebRTC PeerConnection。
- 保存媒体 Track。
- 在 MVP 中跨实例转发媒体。

## 9. 故障处理

### 9.1 用户服务故障

影响：

- 注册、登录、用户查询不可用。
- 已在房间内的用户通话不应被用户服务故障直接中断。

### 9.2 MySQL 故障

影响：

- 注册、登录、用户查询不可用。
- 已建立的会议不依赖 MySQL，可继续运行。

### 9.3 Redis 故障

影响：

- 新房间无法分配媒体实例。
- 加入已有房间无法查询路由。
- 媒体服务多实例协调不可用。

MVP 不要求 Redis 高可用，但部署文档需要说明生产环境应使用高可用 Redis。

### 9.4 媒体实例故障

影响：

- 该实例上的房间中断。
- 新房间不再分配到心跳超时实例。
- MVP 不做房间迁移和自动恢复。

## 10. 部署架构

### 10.1 Docker Compose

本地环境包含：

- `frontend`
- `media-service`
- `user-service`
- `mysql`
- `redis`

本地可以先运行一个媒体服务实例，也需要支持通过 compose 扩展多个媒体实例验证路由。

### 10.2 Kubernetes

K8s MVP 包含：

- Frontend Deployment + Service
- User Service Deployment + Service
- Media Service Deployment + Service
- MySQL Deployment / StatefulSet + Service
- Redis Deployment / StatefulSet + Service
- ConfigMap
- Secret
- Ingress

媒体服务 `replicas` 可以大于 1。实例 ID 可来自 Pod 名称、环境变量或启动时生成的唯一 ID。生产部署应优先使用稳定可观测的实例 ID。

## 11. 架构验收点

- 服务边界清晰，前端、用户服务、媒体服务可以独立启动。
- 用户服务只访问 MySQL。
- 媒体服务只访问 Redis。
- 同一房间所有用户连接到同一个 `mediaInstanceId`。
- Go 媒体服务多个副本同时运行时，新房间可以分配到不同实例。
- Redis 中可以观察到媒体实例心跳和房间路由。
- WebRTC 对象只存在媒体实例内存中。
