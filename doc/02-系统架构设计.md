# StreamForge 系统架构设计

## 1. 架构目标

MVP 架构需要同时满足三个目标：

1. 快速交付可用的视频会议 MVP。
2. 使用 LiveKit 独立集群承载 WebRTC/SFU 能力，降低自研媒体链路风险。
3. 保持服务边界清晰，避免把用户、房间、聊天、媒体、前端状态写混。

## 2. 总体架构

```text
Web Browser
  ├─ REST ───────────────▶ Java User Service ─────▶ MySQL
  ├─ REST room/token ────▶ Go Room Service ───────▶ Redis optional app state
  ├─ WebSocket chat ─────▶ Go Room Service
  └─ LiveKit SDK ────────▶ LiveKit Cluster ───────▶ Redis cluster coordination
```

MVP 由以下组件组成：

| 组件 | 技术 | 职责 |
|:---|:---|:---|
| 前端应用 | Vue 3 + TypeScript + Element Plus + livekit-client | 登录注册、房间页面、视频宫格、聊天、媒体控制 |
| 用户服务 | Java Spring Boot | 注册、登录校验、用户信息查询 |
| 业务数据库 | MySQL | 存储用户账号数据 |
| 房间服务 | Go + REST + WebSocket | 房间创建/加入、LiveKit Token 签发、聊天和业务状态 |
| 媒体服务 | LiveKit Server | WebRTC 信令、ICE、SFU、屏幕共享、媒体状态和参与者事件 |
| 协调缓存 | Redis | LiveKit 集群协调；StreamForge 可保存可过期房间摘要 |
| 部署编排 | Docker Compose + Kubernetes | 本地与 MVP 部署 |

## 3. 核心设计原则

### 3.1 LiveKit 承载媒体事实

MVP 不在 StreamForge Go 服务中创建或保存 WebRTC 对象。以下对象和流程都归 LiveKit 管理：

- WebRTC 信令。
- SDP Offer / Answer。
- ICE Candidate。
- RTCPeerConnection。
- RTP / RTCP。
- 媒体 Track 发布、订阅和转发。
- 屏幕共享 Track。
- 参与者媒体状态。

StreamForge 只通过 LiveKit Token 把用户送入指定 LiveKit 房间。

### 3.2 服务边界

用户服务只关心用户账号数据，不关心房间和媒体。

Go 房间服务关心业务房间、Token 签发、聊天和临时业务状态，不直接访问 MySQL，不直接处理媒体流。

LiveKit 集群关心实时媒体，不访问 StreamForge 用户数据库。

前端负责组合用户服务、房间服务和 LiveKit SDK 的能力。

### 3.3 MVP 简化点

- 不做完整鉴权，登录后前端保存用户基本信息。
- Go 房间服务信任前端加入房间时传入的 `userId` 和 `username`。
- LiveKit access token 只作为 LiveKit 房间准入凭证。
- 不做房间历史和聊天持久化。
- 不在 StreamForge 侧做媒体节点路由和故障迁移。

## 4. 服务职责

### 4.1 前端应用

职责：

- 注册页面。
- 登录页面。
- 创建房间。
- 加入房间。
- 使用 LiveKit SDK 连接房间。
- 房间视频宫格。
- 聊天面板。
- 参与者列表。
- 媒体控制栏。
- 屏幕共享控制。
- WebSocket 聊天连接管理（如果使用 Go WebSocket 聊天）。
- LiveKit 连接状态管理。

前端不直接访问 MySQL、Redis 或 LiveKit API secret。

### 4.2 Java 用户服务

职责：

- 用户注册。
- 登录校验。
- 用户信息查询。
- 密码哈希。
- 用户账号唯一性校验。

用户服务访问 MySQL，不访问 Redis，不处理 WebRTC。

### 4.3 Go 房间服务

职责：

- 房间创建、加入、离开。
- 业务房间 ID 与 LiveKit room name 映射。
- LiveKit Token 签发。
- WebSocket 聊天广播。
- 可过期房间摘要和临时在线状态。
- 健康检查和配置校验。

Go 房间服务可以访问 Redis，不直接访问 MySQL，不处理 SDP/ICE/Track。

### 4.4 LiveKit 集群

职责：

- WebRTC 信令和连接管理。
- ICE / NAT 穿越。
- SFU 媒体转发。
- 参与者状态和媒体 Track 事件。
- 摄像头、麦克风、屏幕共享发布订阅。
- 多节点协调和媒体服务运行时状态。

LiveKit 使用自己的配置和 Redis 协调，不读取 StreamForge MySQL。

## 5. Go 房间服务内部模块

建议分包：

| 包 | 职责 |
|:---|:---|
| `gateway` | HTTP 和 WebSocket 入口、请求上下文、响应封装 |
| `room` | 业务房间、成员摘要、创建/加入/离开 |
| `livekit` | LiveKit 配置、Token 签发、room name 和 participant identity 生成 |
| `signaling` | StreamForge 自有 WebSocket 消息类型、解析、校验、分发 |
| `chat` | 聊天消息校验和房间内广播 |
| `state` | Redis 中的可过期房间摘要和在线状态 |
| `config` | 环境变量、LiveKit、Redis 配置 |
| `log` | 结构化日志封装 |

依赖方向：

```text
gateway -> room
gateway -> livekit
gateway -> signaling
signaling -> chat
chat -> room
room -> state
livekit -> config
state -> Redis
```

## 6. Java 用户服务内部模块

建议包结构：

| 包 | 职责 |
|:---|:---|
| `controller` | REST API 控制器 |
| `service` | 注册、登录校验、用户查询 |
| `repository` | 用户数据访问 |
| `entity` | MySQL 用户实体 |
| `dto` | 请求和响应对象 |
| `config` | 数据源、密码哈希、跨域配置 |
| `exception` | 业务异常和统一错误响应 |

## 7. 关键流程

### 7.1 注册

```text
前端提交 account/password/username
  -> Java 用户服务校验参数
  -> 检查 account 是否存在
  -> 哈希 password
  -> 写入 MySQL
  -> 返回 userId/account/username
```

### 7.2 登录

```text
前端提交 account/password
  -> Java 用户服务查询用户
  -> 校验密码哈希
  -> 返回 userId/account/username
  -> 前端保存用户基本信息
```

### 7.3 创建房间

```text
前端携带 userId/username 请求创建房间
  -> Go 房间服务生成 roomId
  -> Go 房间服务生成 livekitRoomName
  -> Go 房间服务保存可过期房间摘要
  -> Go 房间服务为创建者签发 LiveKit Token
  -> 返回 roomId、livekitRoomName、livekitUrl、livekitToken、appWsUrl
  -> 前端连接 LiveKit 房间
```

### 7.4 加入房间

```text
前端携带 roomId/userId/username 请求加入
  -> Go 房间服务查询业务房间摘要
  -> 房间不存在时返回 ROOM_NOT_FOUND
  -> Go 房间服务为该用户签发 LiveKit Token
  -> 返回 livekitUrl、livekitToken 和可选 appWsUrl
  -> 前端连接 LiveKit 房间
```

### 7.5 LiveKit 音视频连接

```text
前端创建 LiveKit Room 实例
  -> room.connect(livekitUrl, livekitToken)
  -> 启用摄像头和麦克风
  -> LiveKit 发布本地 Track
  -> LiveKit 订阅远端参与者 Track
  -> 前端渲染本地和远端视频
```

### 7.6 聊天

```text
前端连接 appWsUrl
  -> 发送 room.join 或 chat.join
  -> 发送 chat.send
  -> Go 房间服务校验内容
  -> 广播 chat.message 给房间内在线 WebSocket 连接
```

MVP 保留 Go WebSocket 聊天；后续可以迁移到 LiveKit data packet。

## 8. Redis 协调设计

Redis 可用于两类数据：

- LiveKit 集群内部协调数据。
- StreamForge 可过期业务状态摘要。

StreamForge 可保存：

- `streamforge:room:{roomId}:meta`：业务房间摘要。
- `streamforge:room:{roomId}:peers`：临时在线成员摘要。
- `streamforge:chat:{roomId}:recent`：可选短期调试消息，不作为 MVP 持久化聊天记录。

Redis 不负责：

- 保存用户密码。
- 保存永久会议记录。
- 保存 WebRTC PeerConnection。
- 保存媒体 Track。
- 保存 StreamForge 媒体实例路由。

## 9. 故障处理

### 9.1 用户服务故障

影响：

- 注册、登录、用户查询不可用。
- 已经拿到 LiveKit Token 并在房间内的用户通话不应被用户服务故障直接中断。

### 9.2 MySQL 故障

影响：

- 注册、登录、用户查询不可用。
- 已建立的 LiveKit 会议不依赖 MySQL，可继续运行。

### 9.3 Go 房间服务故障

影响：

- 新建房间、加入房间、Token 签发和 Go WebSocket 聊天不可用。
- 已连接 LiveKit 的音视频通话不应立即中断。

### 9.4 LiveKit 故障

影响：

- 该 LiveKit 节点或集群承载的音视频连接中断。
- MVP 不保证通话自动迁移或恢复。
- 前端应展示连接失败并允许重新加入。

### 9.5 Redis 故障

影响：

- LiveKit 多节点协调可能不可用。
- StreamForge 可过期房间摘要和在线状态不可用。
- MVP 部署文档需要说明生产环境应使用高可用 Redis。

## 10. 部署架构

### 10.1 Docker Compose

本地环境包含：

- `frontend`
- `room-service` / 当前代码目录 `media-service`
- `user-service`
- `livekit`
- `mysql`
- `redis`

### 10.2 Kubernetes

K8s MVP 包含：

- Frontend Deployment + Service
- User Service Deployment + Service
- Room Service Deployment + Service
- LiveKit Deployment / StatefulSet + Service
- MySQL Deployment / StatefulSet + Service
- Redis Deployment / StatefulSet + Service
- ConfigMap
- Secret
- Ingress

LiveKit 需要单独规划信令入口、RTC UDP 端口、TURN/TLS 和公网 IP。Go 房间服务可以按普通无状态服务横向扩展。

## 11. 架构验收点

- 服务边界清晰，前端、用户服务、房间服务、LiveKit 可以独立启动。
- 用户服务只访问 MySQL。
- Go 房间服务不创建 PeerConnection、不处理 SDP/ICE/Track。
- Go 房间服务可以签发有效 LiveKit Token。
- 前端可以使用 `livekit-client` 加入指定房间。
- 两个或四个浏览器标签页可以互相看到视频并听到音频。
- Docker Compose 和 Kubernetes 文档中明确 LiveKit 信令、RTC 端口和 Redis 配置。
