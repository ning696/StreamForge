# StreamForge 测试与验收方案

## 1. 目标

测试方案用于保证 MVP 的核心链路可用：

- 用户注册和登录。
- 房间创建、加入、离开。
- Redis 房间级路由。
- WebSocket 信令和聊天。
- WebRTC SFU 音视频通话。
- 屏幕共享和媒体控制。
- Docker Compose 和 Kubernetes 部署。

## 2. 测试分层

| 层级 | 目标 | 示例 |
|:---|:---|:---|
| 单元测试 | 验证纯逻辑和边界条件 | 用户参数校验、房间路由选择、消息解析 |
| 集成测试 | 验证服务与依赖组件协作 | Java + MySQL、Go + Redis、WebSocket 加入房间 |
| 端到端测试 | 验证用户完整流程 | 注册、登录、创建房间、加入房间、聊天 |
| 手工音视频测试 | 验证浏览器媒体能力 | 多标签页音视频、屏幕共享、设备切换 |
| 部署验收 | 验证运行环境 | docker-compose、K8s 多副本媒体服务 |

## 3. Java 用户服务测试

### 3.1 单元测试

覆盖：

- 账号为空。
- 账号长度不合法。
- 密码为空。
- 密码长度不合法。
- 用户名为空。
- 用户名长度不合法。
- 密码哈希和校验。

### 3.2 集成测试

覆盖：

- 注册成功写入 MySQL。
- 重复账号注册失败。
- 正确账号密码登录成功。
- 错误密码登录失败。
- 查询用户信息不返回密码哈希。

建议命令：

```bash
./mvnw test
```

如果项目未使用 Maven Wrapper，则使用：

```bash
mvn test
```

## 4. Go 媒体服务测试

### 4.1 单元测试

覆盖：

- 媒体实例注册数据生成。
- 心跳 TTL 刷新。
- 健康实例筛选。
- 创建房间时选择媒体实例。
- 加入房间时读取已有房间路由。
- 房间不存在时返回错误。
- 聊天消息长度校验。
- WebSocket 消息 envelope 解析。

建议命令：

```bash
go test ./...
```

### 4.2 Redis 集成测试

覆盖：

- 实例启动后写入 `streamforge:media:instances`。
- 实例心跳写入 `streamforge:media:instance:{id}`。
- 创建房间后写入 `streamforge:room:{roomId}:instance`。
- 同一房间多次加入时路由不变化。
- 实例心跳超时后不再分配新房间。

## 5. WebSocket 信令测试

覆盖：

- 连接后未发送 `room.join` 时不能发送 WebRTC 消息。
- `room.join` 成功后收到 `room.joined`。
- 第二个用户加入后，第一个用户收到 `peer.joined`。
- 用户离开后，其他用户收到 `peer.left`。
- 发送 `chat.send` 后，同房间所有用户收到 `chat.message`。
- 无效消息类型返回 `error`。
- 聊天消息超过 1000 字符返回 `MESSAGE_TOO_LONG`。

## 6. WebRTC 手工测试

### 6.1 两人通话

步骤：

1. 打开两个浏览器标签页。
2. 使用两个不同账号登录。
3. 用户 A 创建房间。
4. 用户 B 输入房间号加入。
5. 两个用户允许摄像头和麦克风权限。

通过标准：

- A 能看到 B 的视频。
- B 能看到 A 的视频。
- A 和 B 能听到对方声音。
- 成员列表显示 2 人。

### 6.2 四人通话

步骤：

1. 打开四个浏览器标签页或两台设备。
2. 四个用户加入同一房间。
3. 每个用户开启摄像头和麦克风。

通过标准：

- 每个用户都能看到其他用户的视频。
- 成员列表显示 4 人。
- 关闭任意一个用户摄像头后，其他用户看到该用户摄像头关闭状态。

### 6.3 屏幕共享

步骤：

1. 用户 A 点击屏幕共享。
2. 用户 A 选择屏幕或窗口。
3. 用户 B 观察房间主画面。
4. 用户 A 停止共享。

通过标准：

- B 能看到 A 的屏幕共享画面。
- A 停止共享后，B 的 UI 恢复普通视频布局。
- 成员列表中 A 的屏幕共享状态正确变化。

### 6.4 媒体控制

覆盖：

- 静音。
- 取消静音。
- 关闭摄像头。
- 开启摄像头。
- 切换麦克风。
- 切换摄像头。

通过标准：

- 本地媒体状态变化立即反映在 UI。
- 远端用户收到状态广播。
- 切换设备后通话不中断或可自动恢复。

## 7. 多实例路由验收

### 7.1 Docker Compose 验收

如果本地环境支持启动多个媒体实例，验证：

1. 启动 Redis。
2. 启动至少两个 Go 媒体服务实例。
3. 创建多个房间。
4. 查看 Redis 中不同房间的 `mediaInstanceId`。
5. 同一房间加入多个用户。

通过标准：

- 不同房间可以分配到不同媒体实例。
- 同一房间所有用户对应相同 `mediaInstanceId`。
- 同一房间可以完成聊天和音视频通话。

### 7.2 Kubernetes 验收

步骤：

1. 部署 Redis。
2. 部署 Go 媒体服务，`replicas >= 2`。
3. 部署用户服务、MySQL、前端。
4. 创建房间并加入多个用户。
5. 查看媒体服务 Pod 日志和 Redis 路由。

通过标准：

- 所有媒体服务 Pod 正常注册心跳。
- 新房间分配到健康媒体实例。
- 同一房间用户固定到同一实例。
- 删除某个空闲媒体实例 Pod 后，新房间不再分配到已失效实例。

## 8. 前端测试

覆盖：

- 登录表单校验。
- 注册表单校验。
- 创建房间按钮 loading 和错误状态。
- 加入不存在房间的错误提示。
- 房间页成员列表变化。
- 聊天消息追加。
- 媒体控制按钮状态。
- 移动端布局。

建议命令：

```bash
npm run build
```

如项目引入单元测试框架，再补充：

```bash
npm run test
```

## 9. 部署测试

### 9.1 Docker Compose

通过标准：

- `docker compose up` 可以启动全部服务。
- 前端可访问。
- 用户服务健康检查通过。
- 媒体服务健康检查通过。
- MySQL 可连接。
- Redis 可连接。

### 9.2 Kubernetes

通过标准：

- 所有 Pod 进入 Running。
- Service 可解析。
- Ingress 可访问前端和 REST / WebSocket 入口。
- 媒体服务副本数大于 1。
- Redis 中存在媒体实例心跳。

## 10. 里程碑验收

### M1：用户、信令与路由骨架

必须满足：

- 用户可以注册和登录。
- 用户表写入 MySQL。
- 媒体实例注册到 Redis。
- 创建房间写入房间路由。
- 加入房间读取房间路由。
- WebSocket 可以加入房间。
- 房间内聊天可用。

### M2：多实例 SFU 音视频通话

必须满足：

- Go 媒体服务至少两个实例同时运行。
- 同一房间固定到同一实例。
- 2 人音视频通话可用。
- 4 人音视频通话可用。
- ICE Candidate 交换稳定。
- 用户离开后其他用户收到通知。

### M3：MVP 完成

必须满足：

- 简单用户体系可用。
- 多人音视频可用。
- 屏幕共享可用。
- 媒体控制可用。
- 在线状态可用。
- 聊天可用。
- Docker Compose 可运行。
- Kubernetes Manifest 可部署。

## 11. 回归检查清单

每次较大改动后检查：

- 注册和登录是否仍可用。
- 创建房间是否仍写入 Redis 路由。
- 加入房间是否仍复用原路由。
- WebSocket 消息类型是否和文档一致。
- 两个标签页是否仍能通话。
- 聊天是否仍广播。
- 屏幕共享是否仍可开始和停止。
- docker-compose 是否仍可启动。
