# StreamForge 测试与验收方案

## 1. 目标

测试方案用于保证 MVP 的核心链路可用：

- 用户注册和登录。
- 房间创建、加入、离开。
- LiveKit Token 签发。
- Go WebSocket 聊天。
- LiveKit SFU 音视频通话。
- 屏幕共享和媒体控制。
- Docker Compose 和 Kubernetes 部署。

## 2. 测试分层

| 层级 | 目标 | 示例 |
|:---|:---|:---|
| 单元测试 | 验证纯逻辑和边界条件 | 用户参数校验、LiveKit room name 生成、Token claims、消息解析 |
| 集成测试 | 验证服务与依赖组件协作 | Java + MySQL、Go + Redis、Go Token 签发、WebSocket 聊天 |
| LiveKit 集成测试 | 验证前端能用后端 Token 加入 LiveKit | token 连接、发布音视频、订阅远端 Track |
| 端到端测试 | 验证用户完整流程 | 注册、登录、创建房间、加入房间、聊天、音视频 |
| 手工音视频测试 | 验证浏览器媒体能力 | 多标签页音视频、屏幕共享、设备切换 |
| 部署验收 | 验证运行环境 | docker-compose、K8s、LiveKit RTC 端口 |

## 3. Java 用户服务测试

### 3.1 单元测试

覆盖：

- 账号为空。
- 账号长度不合法。
- 密码为空。
- 密码长度不合法。
- 用户名为空。
- 用户名长度不合法。
- 密码哈希和校验。

### 3.2 集成测试

覆盖：

- 注册成功写入 MySQL。
- 重复账号注册失败。
- 正确账号密码登录成功。
- 错误密码登录失败。
- 查询用户信息不返回密码哈希。

建议命令：

```bash
./mvnw test
```

如果项目未使用 Maven Wrapper，则使用：

```bash
mvn test
```

## 4. Go 房间服务测试

### 4.1 单元测试

覆盖：

- `roomId` 生成。
- `livekitRoomName` 生成。
- `livekitIdentity` 生成。
- LiveKit Token claims 构造。
- Token 有效期配置。
- 创建房间参数校验。
- 加入不存在房间返回错误。
- 聊天消息长度校验。
- WebSocket 消息 envelope 解析。

建议命令：

```bash
go test ./...
```

### 4.2 Redis 集成测试

覆盖：

- 创建房间后写入 `streamforge:room:{roomId}:meta`。
- 加入房间时读取业务房间摘要。
- 房间为空后删除或过期业务摘要。
- 临时在线成员摘要写入和清理。

### 4.3 LiveKit Token 测试

覆盖：

- Token 中包含正确 room name。
- Token 中包含正确 participant identity 和 name。
- Token 中不泄露 API secret。
- 使用错误 secret 生成的 Token 无法连接 LiveKit。
- Token 过期后无法继续用于新连接。

## 5. WebSocket 聊天测试

覆盖：

- 连接后未发送 `room.join` 时不能发送聊天消息。
- `room.join` 成功后收到 `room.joined`。
- 第二个用户加入后，第一个用户收到 `peer.joined`。
- 用户离开后，其他用户收到 `peer.left`。
- 发送 `chat.send` 后，同房间所有用户收到 `chat.message`。
- 无效消息类型返回 `error`。
- 聊天消息超过 1000 字符返回 `MESSAGE_TOO_LONG`。

## 6. LiveKit 手工音视频测试

### 6.1 两人通话

步骤：

1. 启动前端、用户服务、房间服务、LiveKit、MySQL、Redis。
2. 打开两个浏览器标签页。
3. 使用两个不同账号登录。
4. 用户 A 创建房间。
5. 用户 B 输入房间号加入。
6. 两个用户允许摄像头和麦克风权限。

通过标准：

- A 能看到 B 的视频。
- B 能看到 A 的视频。
- A 和 B 能听到对方声音。
- LiveKit 参与者列表显示 2 人。
- Go 房间服务日志不出现 SDP/ICE/Track 处理逻辑。

### 6.2 四人通话

步骤：

1. 打开四个浏览器标签页或两台设备。
2. 四个用户加入同一房间。
3. 每个用户开启摄像头和麦克风。

通过标准：

- 每个用户都能看到其他用户的视频。
- 成员列表显示 4 人。
- 关闭任意一个用户摄像头后，其他用户看到该用户摄像头关闭状态。

### 6.3 屏幕共享

步骤：

1. 用户 A 点击屏幕共享。
2. 用户 A 选择屏幕或窗口。
3. 用户 B 观察房间主画面。
4. 用户 A 停止共享。

通过标准：

- B 能看到 A 的屏幕共享画面。
- A 停止共享后，B 的 UI 恢复普通视频布局。
- 成员列表中 A 的屏幕共享状态正确变化。

### 6.4 媒体控制

覆盖：

- 静音。
- 取消静音。
- 关闭摄像头。
- 开启摄像头。
- 切换麦克风。
- 切换摄像头。

通过标准：

- 本地媒体状态变化立即反映在 UI。
- 远端用户通过 LiveKit 事件看到状态变化。
- 切换设备后通话不中断或可自动恢复。

## 7. LiveKit 部署验收

### 7.1 Docker Compose 验收

验证：

1. 启动 Redis。
2. 启动 LiveKit。
3. 启动 Go 房间服务。
4. 创建房间并获取 Token。
5. 前端使用 Token 连接 LiveKit。

通过标准：

- LiveKit 健康检查通过。
- Go 房间服务可以签发 Token。
- 前端可以加入 LiveKit 房间。
- 同一业务 `roomId` 对应同一 `livekitRoomName`。
- 同一房间可以完成聊天和音视频通话。

### 7.2 Kubernetes 验收

步骤：

1. 部署 Redis。
2. 部署 LiveKit。
3. 部署用户服务、MySQL、Go 房间服务、前端。
4. 创建房间并加入多个用户。
5. 查看 LiveKit Pod 日志、前端连接状态和浏览器 WebRTC 状态。

通过标准：

- 所有 Pod 正常运行。
- LiveKit 信令入口可访问。
- LiveKit RTC UDP 端口按部署说明开放。
- Go 房间服务可以读取 LiveKit Secret 并签发 Token。
- 同一房间用户进入同一个 LiveKit 房间。

npm run test

## 9. 部署测试

### 9.1 Docker Compose

通过标准：

- `docker compose up` 可以启动全部服务。
- 前端可访问。
- 用户服务健康检查通过。
- Go 房间服务健康检查通过。
- LiveKit 可连接。
- MySQL 可连接。
- Redis 可连接。
- 用户可以注册登录。
- 用户可以创建和加入房间。

### 9.2 Kubernetes

通过标准：

- 所有 Pod 进入 Running。
- Service 可解析。
- Ingress 可访问前端和 REST / WebSocket 入口。
- LiveKit 信令入口可访问。
- RTC UDP 端口可用。
- Redis 可供 LiveKit 使用。

## 10. 里程碑验收

### M1：用户、房间与聊天骨架

必须满足：

- 用户可以注册和登录。
- 用户表写入 MySQL。
- Go 房间服务可以创建和加入业务房间。
- WebSocket 可以加入房间。
- 房间内聊天可用。

### M2：LiveKit 多人音视频通话

必须满足：

- Go 房间服务可以签发 LiveKit Token。
- 前端可以使用 Token 连接 LiveKit。
- 2 人音视频通话可用。
- 4 人音视频通话可用。
- 用户离开后其他用户 UI 正确更新。

### M3：MVP 完成

必须满足：

- 简单用户体系可用。
- LiveKit 多人音视频可用。
- 屏幕共享可用。
- 媒体控制可用。
- 在线状态可用。
- 聊天可用。
- Docker Compose 可运行。
- Kubernetes Manifest 可部署。

## 11. 回归检查清单

每次较大改动后检查：

- 注册和登录是否仍可用。
- 创建房间是否仍返回 `livekitUrl` 和 `livekitToken`。
- 加入房间是否进入同一个 LiveKit room name。
- WebSocket 聊天是否仍广播。
- 两个标签页是否仍能通话。
- 屏幕共享是否仍可开始和停止。
- docker-compose 是否仍可启动。
