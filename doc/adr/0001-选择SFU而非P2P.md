# ADR 0001：选择 SFU 而非 P2P

## 状态

Accepted

## 背景

StreamForge 的目标是构建支持 4-8 人多人视频会议的 Web 实时音视频系统。常见架构选择包括：

- P2P：客户端之间直接建立连接。
- SFU：客户端把媒体流上传到服务器，服务器选择性转发给其他客户端。
- MCU：服务器接收所有媒体流后进行混流和转码，再发给客户端。

## 决策

MVP 阶段采用 SFU 架构，不实现 P2P 中间态。

## 原因

### P2P 不适合本项目目标规模

P2P 在 2 人通话中简单且低延迟，但参与者增加时，每个客户端需要向其他所有客户端上传媒体流。4-8 人场景下，客户端上行带宽和连接管理复杂度会快速上升。

### MCU 成本过高

MCU 可以降低客户端带宽压力，但服务端需要编解码和混流，CPU 成本高，实现复杂度也高。MVP 不需要混流能力。

### SFU 更符合 4-8 人会议目标

SFU 让每个客户端通常只上传一份音视频流，服务器负责转发。服务器不做重度编解码，CPU 压力可控，适合 Go 的高并发网络 I/O 场景。

## 影响

正面影响：

- 客户端上行压力低于 P2P。
- 服务端 CPU 压力低于 MCU。
- 架构符合多人会议产品的主流实现方式。
- 后续可以扩展屏幕共享、录制和媒体实例路由。

负面影响：

- 系统需要引入并部署 SFU 媒体服务。
- 客户端下行带宽会随房间人数增加。
- 需要处理 WebRTC 部署、UDP 端口、TURN 和浏览器兼容等问题。

## 约束

- MVP 不做 P2P。
- MVP 不做 MCU 混流。
- MVP 不做服务端视频转码。
- MVP 使用 LiveKit 独立集群承载 WebRTC 与 SFU 能力，StreamForge Go 服务不自研 SFU。
