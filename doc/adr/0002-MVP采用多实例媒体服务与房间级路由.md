# ADR 0002：MVP 采用多实例媒体服务与房间级路由

## 状态

Superseded by ADR 0004

> 本 ADR 保留为历史记录。`livekit-standalone-cluster` 分支已决定采用 LiveKit 独立集群承载 SFU，StreamForge Go 服务不再通过 Redis 维护 `roomId -> mediaInstanceId` 的媒体实例路由，也不再自研 Go SFU。新的实现依据见 `doc/adr/0004-MVP采用LiveKit独立集群承载SFU.md`。

## 背景

WebRTC / SFU 服务和普通 HTTP 服务不同。用户加入房间后，会在某个 Go 媒体服务进程内形成长期状态：

- WebSocket 连接。
- RTCPeerConnection。
- 上行和下行媒体 Track。
- 房间成员状态。
- Track 发布订阅关系。

这些对象不能直接存入 MySQL 或 Redis，也不能在多个进程之间自然共享。

项目要求 MVP 阶段就支持媒体服务多实例部署，因此必须设计多实例协调方式。

## 决策

MVP 采用“媒体服务多实例 + 房间级路由”方案。

核心规则：

```text
roomId -> mediaInstanceId
```

同一个房间内的所有参与者必须连接到同一个媒体实例。Redis 保存房间路由和媒体实例心跳。真实 WebRTC 连接和媒体流只存在对应 Go 媒体实例内存中。

## 方案说明

媒体实例启动时：

1. 生成或读取 `mediaInstanceId`。
2. 向 Redis 注册实例。
3. 周期性刷新实例心跳。

创建房间时：

1. 查询健康媒体实例。
2. 按简单轮询或负载信息选择一个实例。
3. 写入 Redis 房间路由。
4. 返回目标实例连接信息。

加入房间时：

1. 根据 `roomId` 查询 Redis。
2. 找到 `mediaInstanceId`。
3. 连接到该媒体实例。
4. 在该实例内建立 WebSocket 和 WebRTC 连接。

## 为什么不做跨实例媒体级联

另一种方案是允许同一房间的不同用户连接到不同媒体实例，再让媒体实例之间互相转发媒体流。但该方案会引入：

- 跨节点 RTP / WebRTC 转发。
- 媒体级联拓扑。
- 跨节点订阅关系。
- 更复杂的故障恢复。
- 更复杂的带宽和延迟问题。

这些复杂度超过 MVP 范围。

## 影响

正面影响：

- MVP 即可验证媒体服务多实例部署。
- 同房间媒体转发仍保持在单进程内，复杂度可控。
- Redis 协调模型简单清晰。
- 后续可以在此基础上扩展调度、容量监控和实例治理。

负面影响：

- 单个房间容量仍受单个媒体实例限制。
- 某个媒体实例故障会中断其承载的房间。
- MVP 不支持房间自动迁移。
- 部署时必须保证同一房间连接到正确实例。

## 约束

- Redis 只保存路由、心跳、临时在线状态摘要。
- MySQL 不保存媒体实例运行态。
- WebRTC 对象只保存在 Go 进程内存中。
- MVP 不做同房间跨媒体实例级联。
